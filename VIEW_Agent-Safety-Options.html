Decision sheet · Agent safety

The switch says “never executes.”
Right now, it executes anyway.

This page explains one product decision in plain language: what happens when an agent runs, and what “draft mode” should actually do. No code knowledge needed.

Short version:

The “Draft mode only” switch currently changes nothing. The agent writes notes and calendar entries whether it is on or off. Separately, the agent can propose tasks, events, and notes for you to approve. Today an approved “task” lands in the Calendar, but the approval dialog says it lands in Notes.

The recommended fix is Option A: make the switch real, and send approved tasks to the Notes board where people actually look for tasks.

How it works today

Three separate things are getting mixed up. Once you see them apart, the options are simple.

1. What you choose

In the agent editor you pick where output goes: Inbox, Notes, Calendar — or several.

There is also a switch in Advanced:

Draft mode only

“Agent proposes actions but never executes them”

2. What the agent does

When you press Run, the agent:

  • writes an entry to every destination you picked,
  • and may add machine lines like [TASK], [EVENT], [NOTE].

The bug: it never reads the draft switch. The writes happen anyway.

3. What you approve

The machine lines appear in the “Approve agent additions” dialog. Nothing is created until you approve.

Then:

  • Event → Calendar appointment
  • Note → Diary entry
  • Task → Calendar entry of kind “task”

The second bug: the dialog says tasks go to Notes. They do not.

Analogy: it is a fire alarm with a “test mode” switch. The switch looks off, the label says “safe,” but the sprinklers still go off. Nobody is hurt today, but the moment someone relies on that switch, trust breaks.

What “draft mode” should mean

The clean rule is: an agent never writes to your personal surfaces unless you either allow it or approve it.

1
You press Run.The agent gets your data (email, news, etc.) and produces a result.
2
Draft mode ON → the Inbox gets the result.The Inbox is the agent’s report, not a side effect. It should always receive the output.
3
Anything that touches your workspace becomes a proposal.Notes, calendar events, and tasks wait in the approval dialog. Nothing is created silently.
4
You tick what you want and press Add.Only the ticked items are created, each on the surface that matches its type.
5
Draft mode OFF → the agent writes to the destinations you picked.Extra machine-line items can still wait for approval. This is the “I trust this agent” mode.

The four options

They differ in only two ways: whether the switch is real, and where an approved task lands.

Recommended Option A

Make the switch real, and send tasks to Notes

What changes for you: when Draft mode is on, the agent only writes to the Inbox. Everything else becomes a proposal. When you approve a Task, it appears as a card on the Notes board under To Do.

Why: it makes the UI honest, and a task ends up where a task belongs. Calendar stays for events, Notes stays for work items.

  • Inbox still gets the run result.
  • Calendar events still go to Calendar.
  • Diary notes still go to Diary.
  • Tasks go to Notes, not Calendar.
Option B

Make the switch real, but keep tasks in Calendar

What changes for you: same safety behaviour as A, but an approved Task stays a Calendar item and the dialog says “Calendar” instead of “Notes.”

Why: it is the smallest change, but it keeps two different “task” concepts in the product: Notes cards and Calendar task entries. That is the confusion the audit flagged.

  • Less code than A.
  • Tasks remain split across two places.
Option C

Remove draft mode entirely

What changes for you: the switch and its promise disappear. The agent always writes to the destinations you selected. The approval dialog still exists for machine-line proposals.

Why: it is the simplest and most honest if you do not want a safety mode. But it removes the main guardrail before the agent touches your calendar and notes.

  • No misleading switch.
  • No opt-in safety layer.
  • Requires a schema migration to drop the column.
Option D

Keep the behaviour, fix only the wording

What changes for you: nothing about safety. The dialog just stops claiming that tasks go to Notes. The draft switch remains decorative — or gets relabelled to say it only affects proposals.

Why not: the product still says one thing and does another. This is the option that keeps the trust bug alive.

  • Fastest to ship.
  • Does not fix the core finding.

What Option A changes in code

Concrete, so there are no surprises later.

File: agent.runner.ts

Before writing to Notes or Calendar, check agent.draftOnly. If it is on, turn those writes into pending actions instead. The Inbox write stays.

File: agent.actions.ts

Map an approved task item to createTask() (Notes board) instead of createAppointment() (Calendar). Events and diary notes keep their current mapping.

File: RunConfirmModal.tsx

Correct the copy and refresh the Notes store after approval, alongside Calendar and Diary. No more “it’s in Notes” when it is not.

Files: tests + DATAMODEL.md

Add a test proving draft mode writes no notes and no calendar rows, and a test proving an approved task lands on the Notes board. Update the data contract to match.

No database migration is needed for Option A. It uses the existing Task, Appointment, and DiaryEntry models. The only schema change in the whole plan is the separate additive migration for avatarUrl and indexes.

Recommendation

Choose Option A. It is the only option where the switch, the approval dialog, and the actual behaviour all say the same thing — and where a task ends up where you would look for it. The extra work over Option B is one mapping and one store refresh, which is a small price for removing the confusion.

Once you pick, the implementation order is still the same: P0 (correctness and security) → P1 (broken features and state) → P2 (quality, UX, and accessibility), with a checkpoint after each phase.

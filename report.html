Executive summary

What is working, what is pretending to work, and what the next paying customer will hit first.

✓ Real strengths

  • Router → controller → service layering is clean and consistent.
  • Strict TypeScript with zero any in application code.
  • Auth is well designed: bcrypt 12, 15-min access token, refresh digest at rest, single-flight refresh.
  • AES-256-GCM for BYOK keys and OAuth tokens, redacted reads, live key validation.
  • Agent prompt-injection defence is thoughtful: untrusted-data wrapper, truncation, registry gating, approval modal.
  • DATAMODEL.md + AGENTS.md are unusually good operating docs.

✕ Broken as shipped

  • Tool permissions never save. Switch a tool off, reload — it is still on.
  • Draft mode is decorative. The runner writes notes and calendar entries anyway.
  • Template gallery cannot create an agent. It posts slugs the API cannot find.
  • Agent tool API is not scoped to the user — cross-tenant read/write if an ID is known.
  • Profile update always 500s — writes a column that does not exist.
  • Packaged desktop app cannot call the API and runs with nodeIntegration: true.

! SaaS blockers

  • Persisted stores are not namespaced per account → data bleeds between users on one device.
  • No rate limiting on sign-in, signup, reset, or email resend.
  • No CI, no E2E, no component tests; lint fails on a clean checkout.
  • No account settings, search, export/delete, notifications, or audit trail.
  • No error boundary, no structured logs, no error tracking, no metrics.
  • No billing, plans, quotas, or onboarding.

The headline: fix the seven trust-breaking bugs before adding a single feature. A user who toggles a permission off and watches the agent ignore it will not come back.

Findings

49 verified issues. Every item includes the exact location, user impact, and the smallest correct fix.

49 findings
CriticalC1 · Agents
Agent tool permissions never save
AgentEditor.tsx:143–149 · agents.controller.ts:38–53 · agents.service.ts:106–135

The editor PATCHes a tools array, but the Zod update schema has no tools field, so Zod strips it. The service never touches AgentTool. New agents never send tools at all. Result: switching a tool off is a no-op — the backend keeps the template's tools enabled, including calendar_write and note_write.

Fix: persist tools through PATCH /api/tools/agents/:id/tools/:toolName (already exists) on save, diff enabled/removed tools, and add tools to the create payload with registry validation.
CriticalC2 · Agents
Draft mode is decorative — the runner ignores draftOnly
agent.runner.ts:129–198, 373–429 · AgentEditor.tsx:387–404

The UI promises "Agent proposes actions but never executes them". writeOutput() writes notes, calendar appointments, and inbox messages with no draftOnly check anywhere in the runner. Two of the three seeded agents ship with draftOnly: true, so users believe they are in a safe mode while writes happen.

Fix: gate non-inbox destinations on !agent.draftOnly, or convert them to pending actions. If draft-only is meant to be removed, remove the toggle and the promise instead.
CriticalC3 · Agents
Template gallery cannot create an agent
TemplateGallery.tsx:6–55 · AgentEditor.tsx:157–170 · agents.service.ts:57–59

The gallery is a hardcoded array whose id values are slugs (email-summarizer). The editor posts that slug as templateId; the API does findUnique({ where: { id } }) and throws NOT_FOUND. It also lists tools that do not exist (gmail, spreadsheet, search). The real server templates are fetched into the store but never rendered.

Fix: pass the fetched templates into TemplateGallery, accept templateId or templateSlug on the API, and delete the local array.
CriticalC4 · Security
Agent tool API is not scoped to the authenticated user
tools.controller.ts:23–42 · tools.service.ts:35–58

GET /api/tools/agents/:id/tools and PATCH /api/tools/agents/:id/tools/:toolName authenticate the caller but query only by agentId. Any signed-in user who learns another user's agent ID can read and mutate their tool permissions — a classic IDOR in the permission layer.

Fix: join through Agent.userId in both service calls and return 404 when the agent is not owned.
CriticalC5 · Multi-tenancy
Local data bleeds between accounts on the same device
useCalendarStore.ts:118–139 · useDiaryStore.ts:117–161 · all persisted stores

All Zustand keys are global (ontrack-calendar, ontrack-diary…). When the second account has an empty calendar, ensureLoaded uploads the first account's local appointments into it. Diary does the same with its legacy cache. Agents, model-key metadata, and messages also render before the new account's fetch lands.

Fix: namespace every persisted key by userId and clear all stores on sign-out; never upload local state as a seeding strategy in a multi-tenant app.
CriticalC6 · Desktop security
Electron renderer runs with nodeIntegration: true and no CSP
apps/app/src/main/index.ts:61–64, 103–106 · apps/web/index.html

Both windows enable Node in the renderer and expose a preload bridge. Agent output is rendered as Markdown; any future HTML/script injection, compromised dependency, or malicious link becomes arbitrary code execution on the user's machine. The refresh token also lives in localStorage.

Fix: nodeIntegration:false, contextIsolation:true, sandbox:true, a strict CSP, and move the refresh token to Electron safeStorage or an httpOnly cookie.
CriticalC7 · Desktop / packaging
Packaged desktop build cannot reach the backend
apps/app/src/main/index.ts:34–40 · DATAMODEL.md §5

Production loads file://…/dist-web/index.html while every client request uses the relative path /api. There is no VITE_API_BASE wiring. Gmail OAuth also redirects to WEB_URL and relies on same-origin localStorage/cookies. The shipped desktop binary signs up but cannot load data.

Fix: resolve an absolute API origin at build time, use a custom protocol or local server for the app shell, and define the OAuth return path for both hosted and desktop builds.
CriticalC8 · Accounts
PATCH /api/auth/me always fails — avatarUrl is not a column
auth.service.ts:183–193 · auth.controller.ts:25–28 · schema.prisma User

The service builds { name, avatarUrl } and passes it to Prisma. The User model has no avatarUrl field, so every profile update throws at runtime. The UI hides the feature behind a disabled menu item, which is why it has not been noticed.

Fix: add avatarUrl String? plus a migration, or remove it from the schema, service, and DTO until avatar support is built.
CriticalC9 · Auth hardening
No auth rate limits; CORS reflects every origin
index.ts:18–25 · routes/auth.router.ts

Sign-in, signup, refresh, forgot-password, and verification resend are unthrottled. That enables credential stuffing and Resend cost abuse. CORS returns the caller's origin for every request, so any website can call the API from a browser (Bearer tokens limit the blast radius, but it is still an unnecessary surface).

Fix: Cloudflare rate-limit binding or KV counter per IP + per email, exponential backoff, and an explicit allowlist of web origins.
CriticalC10 · Auth reliability
Verification email is fire-and-forget inside a Worker
auth.service.ts:130–132

void sendVerificationMail(...) is not awaited and not registered with executionCtx.waitUntil. Cloudflare may terminate the isolate as soon as the response is sent, so a meaningful share of signups never receive the link and cannot sign in.

Fix: pass c.executionCtx.waitUntil(...) from the controller, or send the mail before responding with a short timeout and a clear retry path.
HighH1 · Agents
Run history is dead code and has the wrong response shape
RunHistory.tsx:40–42 · agent.runner.ts:464–488

The API returns { runs, hasMore }; the component expects an array and calls .slice() on it. It is also imported nowhere, so the promised run-history UI does not exist while the backend already supports it.

Fix: type listRuns as the envelope, mount it in the agent editor or a drawer, and render status, tokens, duration, output, and error.
HighH2 · Performance
Agent list makes one tools request per agent
useAgentsStore.ts:176–186 · agents.service.ts:16–20

GET /api/agents already includes tools, but the store re-fetches tools for every agent with Promise.all. Twenty agents means twenty extra round-trips before the page can render, competing for the same per-request DB pool.

Fix: use the included tools and delete the per-agent fetch.
HighH3 · State
A mutation during first load can strand loadStatus on "loading"
useNotesStore.ts:164–172 · useAgentsStore.ts:172–193 · useAgentMessagesStore.ts:93–110 · useModelKeysStore.ts:81–89

When the epoch changes mid-fetch, the function returns without ever setting loaded or error. The guard then blocks every future ensureLoaded, so the page shows a skeleton until a full reload. Calendar has the opposite problem: no epoch guard at all, so a stale response can overwrite a newer local edit.

Fix: always settle the status in a finally based on whether the epoch still matches, and add the same epoch guard to the calendar store.
HighH4 · Diary
Diary editor can overwrite an entry with an empty body
DiaryEntryPage.tsx:20–34, 51–62

Local form state is initialised once from a possibly-unloaded entry, and the page never calls ensureLoaded(). On a direct link or fresh device, the textarea starts blank; when the store later fills in, the state does not update. Saving then writes the blank content over the real entry.

Fix: call ensureLoaded(), gate the form on the loaded entry, and re-hydrate state when entry.id/content changes.
HighH5 · Consistency
Optimistic agent defaults contradict the server
useAgentsStore.ts:209–228 · AgentEditor.tsx:62–63 · agents.service.ts:85–87

The store fabricates draftOnly:false and maxTokens:4096; the API defaults to true and 2000. Also, the editor defaults draftOnly to false while the backend default is true. The UI can briefly — or permanently, if refresh fails — show the opposite safety posture to what is stored.

Fix: derive optimistic defaults from one shared constant and default the editor to the server value.
HighH6 · Product honesty
The agent editor advertises a billing plan that does not exist
AgentEditor.tsx:422–424

"Budget: 100K tokens/day included. Overage at $0.002 per 1K tokens." The product is BYOK — the user pays their model provider directly, and there is no metering or billing code. This is exactly the kind of copy that becomes a refund request.

Fix: remove the line or show the real per-run estimate from the chosen model key.
HighH7 · Auth data
Verification and reset tokens are stored in plaintext
schema.prisma:40, 50 · auth.service.ts:122–128, 244–251

Refresh tokens are correctly hashed, but email-verification (24 h) and password-reset (1 h) tokens sit readable in Postgres. A database leak becomes account takeover for every pending reset.

Fix: store a SHA-256 digest and compare on use, mirroring the refresh-token pattern.
HighH8 · Security
Agents accept any modelKeyId without an ownership check
agents.service.ts:32–49, 106–135 · agent.runner.ts:294–301

Create and update accept a foreign key ID and the runner then decrypts and uses that key. With an ID from another tenant, an agent can spend another user's model credits.

Fix: verify modelKey.userId === userId before persisting or running; reject with 404.
HighH9 · Reliability
The concurrency lock is an in-memory Set — not a lock on Workers
agent.runner.ts:24, 267–269

Cloudflare runs many isolates. Two requests for the same agent can land on different isolates, both pass the guard, and both run the LLM. The result is duplicate writes and double token spend at the user's expense.

Fix: a DB-backed lock (unique running row / advisory lock) or a Durable Object per agent.
HighH10 · Cost control
Run quota uses server UTC midnight; no monthly budget
agent.runner.ts:271–281

The "50 runs/day" resets at UTC midnight regardless of user timezone, so some users get a short day and others a long one. The spec's monthly token budget, 80% warning, and cost dashboard are not implemented.

Fix: store a per-user timezone and compute the window in it; aggregate tokensUsed per month and expose it before the user hits a surprise bill.
HighH11 · Inbox
Unread badge counts only the first page
useAgentMessagesStore.ts:96–98

unreadCount is computed from the 20 fetched messages. With a full inbox the badge undercounts, and it resets incorrectly after pagination or refresh.

Fix: return unreadCount from the list endpoint (a single count query) and use that.
HighH12 · Agents
Approval copy says approved tasks go to Notes — they go to Calendar
RunConfirmModal.tsx:71–78 · services/agent.actions.ts

The API maps an approved task item to an Appointment with kind:'task', but the modal comment and toast claim the Notes board. Users approve a "task" and then cannot find it where the message told them to look.

Fix: either create a real Task for kind:'task', or correct the copy and refresh the calendar only.

MediumM13 · Reliability

stores/*.ts · api.ts

Writes are optimistic, but a network failure triggers a full refetch and the user's edit disappears. There is no retry, no queued mutation, and no conflict UI for multi-device edits.

MediumM14 · Timer

MediumM15 · Timer
Notification preference can claim "on" while blocked
useTimerStore.ts:169–178 · TimerPage.tsx:237–253

notificationsOn is persisted independently of browser permission. If permission is later revoked, the UI still says "Alerts on" and notifyBrowser silently does nothing.

MediumM16 · Notes
The board loads every task forever
task.service.ts:28–33 · useNotesStore.ts:160–173

GET /api/tasks returns all rows with no pagination or archive. A year of done tasks makes the initial load and every reorder slower, and there is no way to hide history without deleting it.

Fix: archive completed tasks after N days, paginate the done column, and keep the active board bounded.
MediumM17 · Performance
Every drop rewrites both columns row by row
task.service.ts:16–26, 91–138

A move bumps every row by 1,000,000 and then rewrites dense positions, twice (source + target). That is ~2N updates inside one interactive transaction per drag, with unique-constraint pressure. Fine at 20 cards, painful at 500.

Fix: move to fractional/lexicographic ordering so a reorder writes one row, or batch with a single SQL UPDATE … FROM (VALUES …).
MediumM18 · Database
Missing tenant indexes and audit timestamps
schema.prisma:135–166, 188–203, 104–117

Postgres does not auto-index foreign keys. Agent.userId and ModelKey.userId are unindexed, but every list query filters on them. Appointment has no createdAt/updatedAt, so “recently changed” and sync conflict logic are impossible.

Fix: add @@index([userId]) on both, plus timestamps on Appointment (and ideally every mutable entity).
MediumM19 · Scalability
A new Prisma client and TCP pool for every request
db.ts:4–12 · DATAMODEL.md §3

The workaround is documented and correct for local dev, but it costs a handshake per request and never calls $disconnect. At SaaS traffic this is the first latency and connection-limit wall; the spec only suggests Hyperdrive later.

Fix: adopt Hyperdrive (or a Worker-safe pooled driver) before launch and benchmark p95, not just local feel.
MediumM20 · Observability
No structured logs, request IDs, metrics, or error tracking
lib/validate.ts:55 · services/*.ts · backend

Seven console.error calls are the entire production observability story. There is no health endpoint, no p95 latency, no agent success rate, no Sentry, and no alerting. A failed agent run is invisible unless the user reports it.

Fix: structured JSON logs with request IDs, Sentry (or Workers Analytics Engine), and dashboards for auth failures, run success, and DB latency.
MediumM21 · Developer experience
No CI and npm run lint fails on a clean checkout
.github/ · apps/web/eslint.config.js:1

Verified: npm run lint -w web exits 2 with Cannot find package 'eslint-config-turbotron'. There are no workflows at all — only issue templates. Nothing prevents a broken build from merging.

What the tests actually cover

This is the most misleading metric in the repo. The suite reads source files and asserts that strings such as draftOnly, resolveOutputDestinations, and getGmailAccessToken appear — it does not execute a route, render a component, or exercise a database. That is why all seven critical bugs pass 169 green tests.

The fastest way to raise confidence

Add three layers: (1) API integration tests against a disposable Postgres (Hono app.request), (2) React Testing Library for stores and critical forms, (3) 5 Playwright smoke flows — signup → verify → create note → drag → calendar → agent run. Do that before writing new features.

Appendix

Method, assumptions, and what was not tested.

Method

Static review of every application file under apps/web/src, apps/backend/src (excluding the generated Prisma client), and apps/app/src; schema, routes, stores, repositories, runner, Electron main/preload, build config, docs, and tests. Ran npm test, npm run build -w web, and npm run lint -w web in this workspace.

Not exercised

No live database, no Google OAuth credentials, no LLM calls, and no browser interaction session. Findings about runtime behaviour are established from code paths and schema, not observed HTTP responses. The Gmail and agent-run paths are reasoned from source; the three live DeepSeek tests were skipped.

Scoring model

Thirteen dimensions, weights biased toward security and multi-tenant blast radius (security and UI/UX 15% each; backend, code quality 10%; frontend and testing 8%; the rest 4–5%). Weighted score: 6.2 / 10. A score of 10 would mean: no cross-tenant defects, CI + E2E green, observable in production, accessible to WCAG AA, and operable by a paying customer.

Bottom line

Do not launch as a SaaS yet. Ship a private beta only after the ten critical items and the account-namespacing fix are done. The product’s soul — an ADHD-aware companion with genuinely useful agents — is already there. What is missing is the boring layer that makes people trust it with their day.
